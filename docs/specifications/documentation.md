# 文档规范

## 目的

确保每份蓝图文档都能独立理解、方便查找、可以评审，并适合人和 AI 工具使用。

## 必需 Front Matter

每个 Markdown 文档必须以合法 YAML 开头，并包含以下字段：

```yaml
---
title: 易于阅读的文档标题
description: 一句话说明文档目的
status: draft
owner: 负责的团队或角色
last_updated: YYYY-MM-DD
related:
  - relative/path.md
---
```

`related` 始终使用 YAML 列表；尚未建立关联时使用空列表 `[]`。

## 状态词汇

| 状态 | 含义 |
| --- | --- |
| `draft` | 内容未完成或正在评审，不具有强制性。 |
| `proposed` | 内容已足够完整，正在等待决策或批准。 |
| `active` | 已批准，当前具有权威性。 |
| `deprecated` | 过渡期仍可使用，但已不再推荐。 |
| `superseded` | 已被链接的新文档或新决策取代。 |
| `archived` | 仅作为历史保留，不再指导当前工作。 |

## 权威性与资料采信

资料冲突时必须先区分“系统现在怎样运行”和“系统应该怎样运行”，两者不得混写：

- **当前实现事实**：以当前代码、Schema 和测试共同证明的行为为首要证据；再参考当前仓库决策、
  阶段状态和历史记录。迁移文档不得为了符合旧决策或目标设计而改写、隐藏实际代码行为。
- **批准的目标语义**：以迁移期间 Owner 的明确决定和仍有效的 `active` 蓝图决策为准；来源仓库的
  决策和提案用于谱系与取舍说明。新决定取代旧决定时必须更新状态和取代关系。
- **优化候选**：代码审计发现但尚未实现的改进，进入风险、待解决问题或路线图，不使用“当前已支持”
  的措辞，也不反向覆盖现有行为。

代码、Schema 和测试不会仅因已经上线就自动成为永久产品或架构决策；但它们是迁移当前实现事实时的
权威证据。实现与批准目标冲突时，蓝图必须同时记录现状、目标和差距，由 Owner 决定保留现状还是安排
改造，不能让任一层静默覆盖另一层。

## 长期内容边界

实现仓库中的细节只有满足至少一项条件时才应进入蓝图：

- 定义对用户、客户或集成方可观察的行为、契约与兼容性；
- 约束跨组件或跨产品的架构、部署、数据、安全、合规、计费或账务语义；
- 定义稳定的运行、故障、恢复、可观测性或质量要求；
- 对后续实现、迁移或回滚构成长期约束，或者其决策理由需要长期保留；
- 形成可复用的领域概念、术语或生命周期规则。

源码路径、函数和 SQL 实现细节、构建命令、调试日志、原始命令输出、临时实施顺序、
阶段进度和不定义长期行为的原始测试矩阵不进入蓝图。第三方资料应链接到上游权威来源，
不复制为本仓库的第二份文档。实现专用的开发、测试和运维命令继续由对应实现仓库维护。

## 跨仓库迁移

迁移必须按概念整理，不得按原文件或目录结构机械复制。迁移者应先建立来源清单和目标
映射，再分别整理当前实现、批准目标和优化候选；同一概念可以合并多个来源，一份来源也可以
拆分到多个权威位置。历史计划和日志只用于解释背景，不能用来恢复已经被取代的行为。

功能设计描述“当前行为”时必须与代码、Schema 和测试一致。尚未实现的目标只能放在明确标记的目标、
风险、待解决问题或路线图中；不得把优化建议写成现有功能要求。若 Owner 决定以当前代码行为作为长期
语义，应在 ADR 或审核记录中明确批准，并处理与旧决策的取代关系。

迁入的决策必须在正文中保留来源谱系，至少记录：来源仓库和文档、原始 `DEC` 编号、
原始决策日期、来源状态、被取代或修订关系，以及对应的蓝图文档或决策。多个 `DEC`
合并为当前决策时，应逐项列出来源编号；不得重新编号来源决策，也不得因内容已取代而
删除其谱系。

迁入内容必须从 `draft` 或 `proposed` 开始。来源决策有效、代码已经上线或测试通过，
都不能自动使蓝图内容成为 `active`；只有文档的 `owner` 完成评审并明确批准后才能改为
`active`。

来源文档只有在以下迁移门禁全部满足后才能删除：每份来源已有目标映射或明确处置，决策
谱系已经保留，必要内容已经合并且冲突已经处理，相关链接已经更新，仓库校验已经通过，
文档负责人和受影响领域负责人已经完成评审。门禁及具体执行流程见
[贡献指南](../../CONTRIBUTING.md)。

## 写作规则

- 正文默认使用简体中文；产品专名、路径、字段和代码标识符可以保留英文。
- 在开头附近说明目的和范围。
- 陌生术语必须先定义再使用。
- 使用标题、列表和表格明确展示结构。
- 显式记录未知信息与假设。
- 谨慎使用“必须”“应该”“可以”等规范性用语。
- 链接到权威内容，不在第二个位置重新概括。
- 使用仓库相对 Markdown 链接和有意义的链接文字。
- 实现命令和代码导航应留在对应代码仓库。

## 命名规则

目录和文档文件名使用小写 kebab-case。`README.md` 是唯一使用大写的文件名，
作为所在目录的入口。名称应描述产品、架构或业务概念，不描述具体仓库。

## 目录说明

每个文档目录必须包含 `README.md`，并说明：

- 目的；
- 范围；
- 职责；
- 适合存放的内容；
- 不应存放的内容。

## 生命周期

重要变更必须由负责人评审。被取代的文档必须链接到替代文档。已经接受的决策
不得改变原意；需要改变时应新建一条决策并标明取代关系。
