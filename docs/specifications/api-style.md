# API 风格规范

## 目的

为 UnioAPI 产品提供和消费的 API 定义一致、与技术实现无关的规则。

## 适用范围

本规范定义跨产品的公开 API 规则。产品领域负责端点、资源、字段和协议的具体契约；不得把
处理器、数据表、实现框架或测试记录写入本规范。

## 通用规则

### 资源与操作

- 路径使用小写 kebab-case；资源使用复数名词，动作仅用于不能自然表示为资源操作的场景。
- 每个公开操作必须说明认证、权限、幂等性、成功响应、错误、限流和兼容性影响。
- 请求字段必须区分必填、可选、可空与省略。显式零值不能被当作未提供。
- 新字段应保持可选或有安全默认值；修改字段含义、必填性、枚举缩减或响应形状属于破坏性变更。

### 错误与安全

- 客户可见错误必须使用对应公开协议或产品的稳定错误信封；状态码与安全错误码可由调用方处理。
- 内部错误身份与客户文本分离。不得用错误文案驱动重试、权限或账务判断。
- 不得返回凭据、令牌、内部拓扑、完整上游错误正文、堆栈、prompt 或完整响应正文。
- 4xx 错误应说明调用方可修正的安全原因；5xx 使用通用文案并附可关联的请求标识。

### 流式与重试

- 流式协议必须明确首事件、成功终态、用量事件和已开始后错误的形状。
- 流式首个客户可见事件前可以重试或 fallback；之后不得替换上游结果或伪造成功终态。
- 自动重试必须可审计。每次真实外部调用都应有独立的调用记录和成本归因。
- 客户断开不应使已产生的可结算事实丢失；后续收口不得依赖已取消的客户上下文。

### 版本与兼容性

- 公开 API 采用演进优先：新增可选字段、增补响应字段和新增端点通常兼容；仍须记录客户可见影响。
- 破坏性变更必须先发布迁移说明、替代方案、弃用期限和移除条件，并获得领域 owner 批准。
- Provider 或实现限制不能被伪装为协议兼容性；产品文档必须区分接收、适配、拒绝和可审计 Drop。
- 弃用期间保留旧行为的契约测试和可观测性，直至已声明的移除条件达成。

### 可观测性

- 服务端生成业务请求标识；客户关联标识只能用于链路关联，不能替代业务主键。
- 公开契约应说明可供支持人员关联的标识、可观察的状态和不保存的敏感数据。
- 审计记录只保留完成支持、计费、合规或恢复所需的最小事实。

## 证据与采用

每项新增强制规则必须包含设计依据、正确示例、反例以及采用或迁移说明。规则初始为 `draft`；
跨产品或破坏性选择应先以 `proposed` ADR 评审，批准后才可成为 `active` 规范。

## 边界

接口清单与处理器实现属于对应产品领域或代码仓库。
