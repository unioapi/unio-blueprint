# 编码规范

## 目的

定义不受语言和产品限制、所有实现仓库都应遵守的工程要求。

## 工程基线

以下要求保持 `draft`，在工程团队批准前不得作为已生效的跨仓库硬性门禁。

### 正确性与变更边界

- 变更应保持可读、可审查且范围与目标相称；不能以重构或测试通过掩盖行为变化。
- 有外部副作用、持久事实或异步恢复的操作应有稳定标识、明确终态和幂等处理；结果未知时保留
  可审计的恢复路径，而非猜测结果。
- 已开始的业务工作应按既定契约收口、补偿或记录待恢复状态。不得为简化错误处理而抹除已
  经发生的事实。
- 变更影响公开契约、数据、授权、计费、运行状态或恢复语义时，必须评估兼容性、迁移、回滚
  和可观察的失败行为。

### 测试与运行证据

- 测试层级和证据应与风险、影响范围和不可逆性相匹配，覆盖正常、失败、重试、取消和恢复等
  相关场景。
- 共享状态、并发、版本切换或外部调用的变更应验证原子性、幂等性和迟到结果不会覆盖当前事实。
- 运行证据应说明已验证的行为与已知边界；它不能替代蓝图或负责人对长期语义的批准。

### 依赖与供应链

新增依赖或托管能力前，应记录并评估：业务核心性、成熟度、维护活跃度、许可证、安全与漏洞
响应、失败模式、数据处理、替换可行性，以及是否把第三方类型泄漏到核心业务接口。

核心业务逻辑应保持可审计、可测试和可解释。通用基础设施、安全、协议解析、可观测性和精度
计算应优先评估成熟方案；“减少依赖数量”本身不是决策目标。安全和加密能力不得因追求自研而
绕过成熟标准实现。

### 安全、隐私与可观测性

- 密钥、认证材料、用户内容、个人数据和内部拓扑必须按最小必要原则处理；不得写入不受控的
  日志、指标、追踪或错误响应。
- 错误应区分可安全对外表达的契约信息与仅供受控诊断的内部细节。
- 需要跨组件诊断的工作应使用[日志规范](logging.md)定义的关联和数据保护约束。

### 生成物与实现资料

生成代码、构建产物、仓库目录、语言格式和具体命令由各实现仓库负责。它们不能单独定义平台
的长期架构或产品行为。

## 变更计划与蓝图交接

可能改变长期产品、架构、数据、安全、计费、兼容性或运行语义的实现变更，必须遵循以下
交接流程：

1. 编码前在实现仓库建立临时变更计划，说明拟变更语义、影响范围、验证与回滚方式，
   并列出可能受影响的蓝图文档。变更计划用于协作，不是长期权威来源。
2. 按计划完成实现和与风险相匹配的测试，保留足以证明实际行为的代码、Schema 和测试
   证据。实现与当前蓝图冲突时，必须显式记录并交由负责人裁决，不能以测试通过代替批准。
3. 实现和测试通过后，将已经确认的长期语义、约束和决策理由更新到蓝图；实现步骤、日志
   和临时状态不随之迁入。蓝图内容仍须按照文档生命周期完成负责人评审。
4. 蓝图交接、链接更新和校验完成后，临时变更计划才可以按实现仓库规则删除或归档。

每项已完成的实现变更都应有明确的蓝图影响结论。若变更不产生长期语义，可以标记为
“无需更新蓝图”，但必须记录理由；典型情况包括不改变行为的内部重构、仅补充测试，或
使实现重新符合现有蓝图的缺陷修复。是否需要更新由长期语义是否改变决定，而不是由改动
规模、文件数量或测试是否通过决定。

代码、Schema 和测试只作为实现证据参与判断，其资料优先级和迁移边界遵循
[文档规范](documentation.md)。

## 边界

语言格式、构建命令、目录布局和框架指南属于各代码仓库。本文只保留跨仓库基线。
