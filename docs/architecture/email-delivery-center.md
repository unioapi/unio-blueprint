# 架构设计：邮件投递中心

## 摘要

UnioAPI 计划建设统一的邮件投递中心，为验证码、密码重置、余额提醒、充值结果和运维告警等事务性消息提供
可配置、可审计、可恢复的发送能力。平台采用服务商无关的 SMTP 边界：运营人员可以接入任意符合要求的
SMTP 服务商，并在服务商完成域名验证后使用 `noreply@自有域名` 等自定义发件地址。

邮件正文样式由 UnioAPI 的模板系统决定，实际投递链路由 SMTP 服务商决定。可见发件人域名不能用于判断
底层服务商，平台也不提供邮箱账号、域名注册或收件箱托管。

本文描述尚未交付的目标能力，不表示当前平台已经支持邮件发送或模板管理。

## 背景与约束

- 客户身份、账务和运营事件将产生验证码、密码重置、余额变化和告警等邮件需求。
- 平台不能绑定单一邮件服务商，否则会增加迁移成本并限制不同部署环境的选择。
- 自定义发件人后缀依赖域名所有权和邮件服务商验证，不是应用程序可以单独提供的能力。
- 模型请求等主要业务链路不能因 SMTP 延迟或故障而同步阻塞。
- SMTP 密码、收件地址和模板变量可能包含敏感信息，必须遵守最小暴露和可审计原则。
- Sub2API 的通用 SMTP 与模板管理能力只作为功能参考。UnioAPI 应按自身边界重新实现，不直接复制其
  LGPL-3.0 源码或官方 HTML 模板。

## 目标

- 提供不绑定供应商的 SMTP 投递能力，支持隐式 TLS 和 STARTTLS。
- 支持自定义发件人名称、发件地址和经过邮件服务商验证的自有域名。
- 统一管理中文、英文邮件模板、主题、变量、预览和默认模板恢复。
- 使用持久化任务和 Worker 异步投递，提供幂等、有限重试和明确终态。
- 通过 Admin 提供 SMTP 配置、连接测试、测试邮件和模板管理体验。
- 保留足够的投递事实、指标和审计记录，以便判断任务是否创建、是否尝试、是否被服务商接受以及为何失败。

## 非目标

- 提供邮箱账号、收件箱、域名注册、MX 托管或收件服务。
- 在首个版本建设营销群发、联系人分组、订阅活动或邮件增长分析平台。
- 在本文中指定唯一 SMTP 服务商、套餐或生产域名。
- 让模型请求、账务结算等主要业务链路直接同步调用 SMTP。
- 仅凭 SMTP 返回成功承诺邮件一定进入收件箱；最终送达、退信和投诉能力取决于服务商支持。
- 固化具体页面布局、数据库表名、接口路径或实现仓库结构。

## 当前状态

截至 2026-08-03，邮件投递尚未作为 UnioAPI 平台的权威能力交付。当前没有可由 Blueprint 声明为现有事实的
通用 SMTP 配置、邮件模板管理、持久化投递任务或 Admin 邮件管理体验。

## 目标架构

### 组件与职责

| 组件或领域 | 职责 | 负责内容 | 不负责内容 |
| --- | --- | --- | --- |
| 业务事件生产方 | 提出一次事务性通知需求 | 事件类型、收件人、语言、业务幂等键和模板变量 | 连接 SMTP、拼装邮件协议或执行重试 |
| 邮件编排服务 | 将业务事件转换为可投递任务 | 校验事件、选择模板和语言、建立投递事实、执行幂等保护 | 长时间占用业务请求等待邮件送达 |
| Admin 管理面 | 管理邮件能力 | SMTP 配置、连接测试、测试邮件、模板编辑、预览和恢复默认模板 | 暴露 SMTP 密码或伪造送达结果 |
| 配置与密钥边界 | 保存发送身份和凭据 | SMTP 地址、端口、认证信息、TLS 策略、发件人名称和地址 | 向读取接口、日志或审计记录返回密码明文 |
| 持久化投递事实 | 保存任务生命周期 | 事件、收件人、模板版本、状态、尝试次数、时间和安全错误摘要 | 代替邮件服务商的最终送达与投诉事实 |
| Worker 投递执行面 | 执行外部发送 | 独占领取、模板渲染、SMTP 提交、有限重试和终态收口 | 承担 Admin 页面职责或阻塞主要业务流量 |
| SMTP 服务商 | 接收并投递邮件 | 域名验证、SPF/DKIM 对齐、SMTP 接收、互联网邮件投递 | 决定 UnioAPI 邮件正文模板和业务触发规则 |

### 数据与控制流

1. 业务事件生产方提交事件类型、收件人、语言、变量和业务幂等键。
2. 邮件编排服务校验事件并创建持久化投递任务。需要与业务事实原子一致的场景应采用事务性 Outbox，避免
   “业务已成功但邮件任务丢失”。
3. Worker 独占领取任务，使用任务绑定的模板版本和变量生成主题与 HTML 正文。
4. Worker 通过已配置的 SMTP 连接提交邮件，并将任务推进为 `sent` 或记录一次失败尝试。
5. 可重试错误按照有上限的退避策略重新排队；不可重试错误或超过尝试上限后进入 `failed`。
6. Admin 读取投递事实和安全错误摘要进行排查，不读取 SMTP 密码，也不以 `sent` 冒充最终进入收件箱。

验证码和密码重置等用户正在等待的场景，可以对“任务已创建”或“一次有界 SMTP 提交结果”提供及时反馈，
但不得退化为无上限同步等待。余额提醒、充值通知、周期报告和运维告警默认异步执行。

### 自定义发件域名

平台允许运营人员配置发件人名称和发件地址，例如 `UnioAPI <noreply@unioapi.com>`。启用生产发送前，运营
人员必须在所选 SMTP 服务商完成域名验证，并按服务商要求配置 SPF、DKIM 和 DMARC。是否需要 MX 记录取决于
该域名是否还承担收件职责。

应用配置只能声明希望使用的发件地址；SMTP 服务商有责任校验该地址是否属于已授权域名，并可能拒绝或重写
未授权地址。Admin 的连接测试和测试邮件必须分别说明“认证连接成功”和“邮件提交成功”，不能把两者等同于
最终送达。

## 首个版本范围

### 发送与配置

- 通用 SMTP 地址、端口、认证信息和 TLS 策略。
- 自定义发件人名称和发件地址。
- SMTP 连接测试和指定收件人的测试邮件。
- 生产环境禁止未经加密的 SMTP 凭据传输；TLS 校验证书失败时不得降级为明文发送。

### 模板

- 按事件和语言维护邮件主题与 HTML 正文。
- 首批支持中文和英文；缺失语言模板时使用明确的默认语言策略。
- 支持变量清单、带安全示例数据的预览、保存自定义版本和恢复 UnioAPI 默认模板。
- 普通文本变量默认进行 HTML 转义；只有明确声明为可信 HTML 的受控变量可以作为 HTML 片段插入。

### 首批事件

| 类别 | 事件 |
| --- | --- |
| 身份安全 | 邮箱验证码、密码重置 |
| 账务 | 余额不足提醒、充值成功 |
| 运营 | 运维告警 |

新增事件必须定义触发条件、幂等边界、收件人来源、模板变量和敏感信息规则，不能只增加一段 HTML。

### 投递状态

| 状态 | 含义 | 允许的后续动作 |
| --- | --- | --- |
| `pending` | 任务已经持久化，尚未被执行 | Worker 领取 |
| `sending` | Worker 已独占领取并正在提交 | 成功、重试或租约过期后恢复 |
| `sent` | SMTP 服务商已接受本次提交 | 记录提交事实；不自动解释为进入收件箱 |
| `failed` | 不可重试或达到尝试上限 | 运营排查后重新触发新的任务 |

业务幂等键必须阻止同一业务事件在平台内被重复创建。由于 SMTP 提交成功与本地状态写入之间可能发生进程
崩溃，系统只能在通用 SMTP 边界提供尽力避免重复的至少一次交付语义；对重复极其敏感的事件必须在模板和
业务流程中避免产生重复副作用。

## 质量属性

| 场景 | 目标 | 设计响应 |
| --- | --- | --- |
| SMTP 服务变慢或不可用 | 不拖垮主要业务链路 | 持久化任务、独立 Worker、有界连接与读写超时 |
| Worker 在处理期间退出 | 任务最终可恢复 | 独占租约、超时回收和幂等领取 |
| 同一业务事件被重复提交 | 不产生平台内重复任务 | 业务幂等键和唯一性约束 |
| 模板在任务排队后被修改 | 已创建任务的内容可解释 | 任务关联明确的模板版本和变量快照 |
| 凭据错误或域名未授权 | 快速暴露可操作原因 | 独立连接测试、测试邮件和安全错误分类 |
| 邮件量突增 | 保护 SMTP 服务和平台资源 | Worker 并发上限、发送速率边界和队列积压指标 |

## 故障与恢复

- 网络超时、临时服务端错误和服务商限流属于可重试候选，但必须使用有上限的退避，不得无限重试。
- 认证失败、发件人未授权、收件地址格式错误和模板渲染失败默认不可重试，修复配置或数据后创建新任务。
- `sending` 任务必须有租约或等价恢复边界，Worker 退出后能够重新进入处理流程。
- 测试邮件与正式业务邮件使用相同发送链路，但必须标记来源，避免污染正式业务统计。
- SMTP 只证明服务商接受提交。若未来需要可靠的退信、投诉和最终送达状态，应另行引入服务商 Webhook 或
  专用投递 API，并建立新的可信事件边界。

## 安全与隐私

- SMTP 密码必须加密保存，并作为只写敏感配置处理；读取接口只返回“已配置”状态。
- 日志、审计记录、指标和错误响应不得包含 SMTP 密码、完整验证码、密码重置令牌或不必要的邮件正文。
- 只有授权运营人员可以修改 SMTP 配置和模板、发送测试邮件或重新触发失败任务，相关操作必须可审计。
- 模板预览必须隔离不受信任 HTML，防止在 Admin 中执行脚本或访问管理会话。
- 收件地址、模板变量和投递事实应遵守数据最小化及保留策略；具体保留期限在实施前由产品、安全和运营共同
  决定。

## 可观测性

平台至少应提供以下事实：

- 按事件、状态和服务商结果分类的任务数量与成功率；
- 从任务创建到 SMTP 接受的排队时长和提交时长；
- 当前积压、最老任务年龄、重试数量和最终失败数量；
- 不含凭据与正文的错误分类、尝试时间和执行实例标识；
- SMTP 配置和模板的变更审计，以及测试邮件与正式邮件的来源区分。

## 部署与迁移

1. 先建立配置与密钥边界、默认模板和持久化投递事实。
2. 再交付 Worker 领取、SMTP 提交、重试、租约恢复和可观测性。
3. 随后交付 Admin 配置、连接测试、测试邮件、模板编辑和投递记录体验。
4. 最后按事件逐项接入业务生产方，优先身份安全，再接入账务和运营事件。

上线前必须使用真实测试域名验证 SPF、DKIM、DMARC、TLS、垃圾邮件表现和主流邮箱客户端渲染。回滚时可以
暂停 Worker 领取而保留 `pending` 任务，不得通过删除任务掩盖未投递事实。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 通用 SMTP + UnioAPI 模板与任务系统 | 服务商可替换、部署选择多、边界清晰 | 退信和投诉能力不统一 | 首个版本采用 |
| 直接绑定某一家邮件 API | Webhook 和投递状态可能更完整 | 供应商锁定、迁移成本高 | 暂不采用 |
| 业务请求同步发送 SMTP | 实现表面简单 | 延迟和故障直接传导到客户请求 | 不采用 |
| 直接复制 Sub2API 实现与模板 | 起步快 | 不符合 UnioAPI 边界，并产生 LGPL 合规与长期维护问题 | 不采用，独立实现 |

## 风险与待解决问题

以下事项不阻塞记录目标架构，但必须在实施计划中由对应负责人决策：

| 决策点 | 建议 | 适用场景与影响 |
| --- | --- | --- |
| 首个生产 SMTP 服务商 | 优先选择事务邮件服务，而不是个人或普通企业邮箱 | 验证码和告警需要稳定并发、域名信誉和清晰限额；普通邮箱适合低量测试，不适合规模化投递 |
| 投递记录保留期限 | 长期保留状态和错误分类，正文仅在明确排障需要下短期、加密保留 | 长期保存完整正文会扩大隐私和泄露风险；完全不留内容则降低复杂模板问题的排查能力 |
| 重试次数与退避参数 | 按错误类别配置有限重试，并对验证码设置更短有效窗口 | 验证码迟到后价值很低；账务通知和运维报告可以接受更长恢复窗口 |
| 退信与投诉 | 首个版本不承诺统一能力；出现信誉或送达治理需求时再选择 Webhook 集成 | 通用 SMTP 没有统一回执模型，提前抽象会产生无法验证的伪统一接口 |
| 营销邮件 | 首个版本只做事务和运营邮件 | 营销邮件涉及退订、偏好、合规和频率治理，应作为独立产品能力评审 |

## 验证方式

- SMTP 单元和集成测试覆盖隐式 TLS、STARTTLS、认证失败、超时和发件人拒绝。
- Worker 测试覆盖幂等创建、独占领取、崩溃恢复、有限重试、终态和积压保护。
- 模板测试覆盖中英文、变量校验、HTML 转义、可信片段和安全预览。
- 端到端测试覆盖 Admin 配置、连接测试、测试邮件、模板编辑和至少一个真实业务事件。
- 使用真实域名和测试收件箱检查邮件头中的 SPF、DKIM、DMARC 结果及主流客户端展示。

## 相关决策

当前尚未建立全局 ADR。若实施中需要绑定特定邮件服务商、改变事务一致性边界或承诺最终送达语义，必须在
[全局决策](../decisions/README.md)中新增记录，不能静默改变本文边界。
