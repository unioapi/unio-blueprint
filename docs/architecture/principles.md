# 架构原则

## 文档状态

以下原则由 Gateway 迁移资料提炼，尚未得到架构团队批准，全部保持 `draft`。它们用于形成可
评审的共同语言，不替代[全局决策](../decisions/README.md)或领域级规则。

## 候选原则

### 1. 明确边界与状态所有权

进程、持久业务数据、共享运行态和外部上游应具有明确且不重叠的职责。长期业务事实必须由
可审计的持久机制承担；共享运行态只在其可验证的协调范围内使用。

适用于：多实例运行、异步恢复、配置发布及任何涉及外部调用的流程。

取舍：需要额外定义恢复、版本和观测边界，但避免临时缓存或上游响应被误当作权威事实。

### 2. 先守住公开契约和业务事实

跨组件演进应保持已承诺的协议和业务事实可解释。无法继续支持的行为必须通过明确的兼容、
迁移或弃用决策处理，不能由内部实现变化静默改变。已开始并形成事实的工作应继续收口、
补偿或留存可恢复记录，而不是被事后抹除。

适用于：协议适配、计费、授权、异步任务、状态迁移和外部依赖故障。

取舍：兼容和恢复会增加实现与验证成本，但避免客户行为、审计记录和实际外部副作用相互矛盾。

### 3. 不可信控制面时安全收敛

当授权、限额、协调或外部调用依赖的控制状态无法验证时，受影响的新操作应 `fail-closed`；
返回安全的错误，同时允许已开始的业务事实按既定生命周期收口。

适用于：共享运行态不可用、配置版本不一致、关键依赖尚未就绪或恢复完整性无法证明的情况。

取舍：短期可用性会下降，因此必须用高可用设计、清晰的 `readiness`、可观测性和恢复演练降低
停机时间；不得以 `fail-open` 制造不可解释的调用或越权。

### 4. 恢复必须可审计且幂等

每项可能重试、补偿或延迟完成的工作都应有稳定标识、明确终态和可审计的处理结果。重复执行
不得制造重复副作用；结果未知时应记录并按可验证事实恢复，而非猜测成功或失败。

适用于：请求处理、账务、任务队列、配置发布、租约及状态恢复。

取舍：需要保留足够的事实和恢复流程，但能限制故障、进程中断与网络重试造成的不一致。

### 5. 依赖服务于可维护的边界

依赖选择以成熟度、安全性、许可证、维护性、失败模式、可替换性及与核心边界的耦合为依据，
不以“依赖越少越好”为目标。产品核心逻辑应保持可审计、可测试和可解释；通用基础设施、
安全、协议解析、可观测性和精度计算应优先评估成熟方案。

适用于：新增第三方库、平台服务或托管基础设施。

取舍：引入依赖会增加供应链治理，但为常见且高风险的通用能力重复造轮子通常会增加长期风险。
